# Evaluate a complete Agent CLI Runtime with application policy outside it

The target Rust design owns Agent CLI execution, PTY input/output, process lifecycle, vendor adaptation, session identification and log observation as one coherent runtime module. The shared PTY core also serves ordinary shell terminals to avoid maintaining separate Python and Rust implementations of input, resize, backpressure and cleanup; ordinary shells do not acquire agent-specific vendor or observation behavior. Unrelated backend subprocesses and non-interactive CLI calls remain outside the migration scope. Python retains existing outward interfaces, application coordination, durable application persistence, credential and quota policies, and injection policy/configuration-writing implementations. CLI-specific command, argument and path composition are additional Rust migration candidates; Python injection handlers may delegate these mechanics without moving their policy or effects. Prefer structured program/arguments/cwd/environment and established standard-library or PTY command builders, serializing shell text only at an explicit shell interface. Preserve login-shell behavior, Windows executable/npm-shim resolution, nested hook/config quoting and existing injection ordering and launch handshakes. General application paths and unrelated subprocesses are not included, and no crate is selected merely because it advertises cross-platform support. Splitting execution ownership between Python and Rust would reduce initial migration scope but leave cancellation and observation consistency crossing that boundary; the adapter-only alternative remains part of the cost comparison, not the selected complete target.

This defines the evaluation boundary, not migration authorization. Python connects to the runtime through a standalone sidecar, following the existing STT subprocess integration, binary lookup and packaging conventions rather than introducing a native Python library. This reuses an established delivery boundary but adds IPC costs that must be evaluated; CLI streaming and lifecycle policies are designed separately, without refactoring STT. When Rust is selected, a missing binary, startup failure or incompatible protocol must surface as a runtime failure, never trigger automatic fallback to Python. Python may be explicitly selected as the evaluation baseline, but must not rescue a failed Rust run or make its verification appear successful. Each Python backend owns one sidecar across its workspaces and windows, preserving the current app-level terminal ownership rather than adding a process per workspace or pane. Session ownership remains workspace- and pane-scoped, and a WebSocket disconnect does not terminate the runtime or its sessions. This avoids additional resident processes and cross-runtime coordination but gives a runtime-wide crash a backend-wide impact. Such a failure invalidates affected requests and requires identity-verified cleanup of the runtime's sessions and descendants, without overlapping replacement launches. Preserve existing error presentation and conditional conversation recovery: enabled auto-resume applies only to panes visible when loss is reported, through the existing resumability and session-existence checks; other panes retain manual Rebuild. Do not promise seamless recovery of the original PTY or replay pending input. Python remaining alive while the sidecar dies requires explicit runtime-scoped failure detection, cleanup and notification; the existing backend-startup orphan reaper alone is insufficient. Observation and parsing failures retain the existing Python behavior as the migration baseline; changing inference, fallback or externally visible error semantics requires a separately agreed correction. Shared vendor declarations and composed vendor strategies follow the existing semantic constraints; capability integration status distinguishes integrated, vendor-unsupported and not-yet-integrated, with verification evidence recorded separately rather than treating missing integration as native vendor incapability.

Evaluate a minimal Rust end-to-end implementation before completing every vendor adapter: include PTY streaming, cancellation and cleanup, session observation and the retained Python injection interface. The design inventory still covers all supported vendors. Verify locality with materially different existing vendor behavior, not just one vendor's happy path: adding an adapter or changing behavior within an existing capability must stay in its declaration, adapter and tests rather than introduce vendor branches into shared orchestration. Measure the combined Python-and-Rust cost against the existing Python baseline. A negative result may stop the Rust evaluation early; a positive result only supports continuing it, not formal adoption. Formal adoption still requires all supported vendor contracts and three-platform packaging and actual Python-to-Rust interface verification to pass in the fork's Actions. This is not a separately delivered Python consolidation or a split product delivery, and it does not authorize implementation.
