## 5. Primary benefit: external Node/pnpm removed from all daily JavaScript work?

**Not established. It is achieved for install, typecheck and build on Linux and Windows at HEAD, and for install and typecheck on macOS at HEAD; it is not achieved for the daily test suite, and macOS build/startup are unmeasured at HEAD.** Evidence behind the positive part: the Bun candidate ran with a PATH that held no `node`, `npm`, `npx` or `pnpm` on all three platforms (Linux and Windows add a sampling-based, non-exhaustive census of the correctness job's child executables, which covers install, typecheck, builds and tests; macOS at HEAD only the controlled PATH). Bun-only startup is not established on any platform at HEAD: the readiness job's single process-table snapshot per platform (Linux 16, Windows 12 case-owned processes; receipts CIRR) records no executable path for its node-named child, a PATH-by-name check cannot exclude an absolute-path launch of an external node, one snapshot is not a census, and the Windows snapshot is of a failed start. No mise or other version manager took part: the pinned Bun binaries were verified against publisher checksums or recorded by hash, and the exact-version guard needs no manager. Against it:

- **Remaining pnpm-dependent test.** `src/main/plugins/pluginExternalWorkspace.test.ts` spawns `pnpm` when `NAVIDE_PNPM`/`npm_execpath` do not name it, so Bun-only `test:run` fails on every platform (`Executable not found in $PATH: "pnpm"`). The residual has two layers (CB-E10): layer 1 is the shipped helper; layer 2 is a Bun 1.4.2 limit (non-optional peers of `file:` tarballs resolve from the registry; no install shape worked, only a manifest `overrides` change that alters what the test proves). Layer 2 was measured on macOS pre-rebase and not re-tested on Linux/Windows. User decision A (2026-10-11) accepts the gap; fixing either layer alone has not been shown to suffice.
- **The `node` name remains.** The daily scripts still call `pnpm run ...` (9 scripts) and `node scripts/bun/vue-tsc.cjs` (7 scripts). They work because Bun rewrites nested `pnpm run` to `bun run` and the dispatcher exposes a private temporary `node` symlink to Bun; on Windows that symlink is not command-resolvable (needs `node.exe`) and the route instead re-enters through `Bun.which('bun')`. The processes are Bun, but contributors see `node` in process tables, and the Windows alias is untested for non-admin symlink privilege.
- **The canonical route is an evaluation dispatcher.** `bun scripts/bun-evaluation.mjs <check|install|run|pack|audit>` enforces the pin and an allowlist (`dev` yes, `start` and arbitrary scripts no). Plain `bun install` / `bun run` bypass the pin; whether `engines.bun` is enforced by them was not tested.
- **Two lockfiles, one stale for the other toolchain.** `package.json` now uses `workspace:*` while `pnpm-lock.yaml` still records `link:`; `pnpm install --frozen-lockfile` fails on the branch (accepted at checkpoint A), so the Node control uses the base tree plus overlay files. Adoption would need a lock-ownership decision.
- **Outside the daily scope but product-visible:** the default `context7` MCP integration launches through `npx` and fails to start in a Bun-only environment (startup stays healthy).
- **Release/CI isolated Node:** allowed by design, unchanged and not run with Bun (`not-run`).
