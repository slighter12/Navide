# Ordinary-shell, Claude reference and native-difference runtime evaluation

A standalone Rust executable owns native PTY/process lifecycle for ordinary shells. Python retains authenticated WS/Plugin contracts, application routing, command wrapping, durable ownership and binary output presentation. Default execution is unchanged Python; explicit isolated-harness evaluation selection is `NAVIDE_ACR_EVAL_RUNTIME=rust-shell` with `NAVIDE_REGRESSION_ROOT` set. Selected-Rust failures never spawn a Python PTY. The Claude reference slice additionally composes native JSONL interpretation and its existing shutdown strategy below; the ticket-04 slices validate Codex and OpenCode native differences through the same interface. Cancellation, runtime-loss cleanup and conversation-recovery validation (ticket 05) are in the section below. Other complete agent integrations, packaging and CI are not delivered by these slices.

## Build and applicability

Build explicitly before tests: `cargo build --offline --locked --release --manifest-path native/navide-cli-runtime/Cargo.toml`. The evaluated host uses the already-installed Rust 1.99.0 macOS ARM64 toolchain and cached lockfile dependencies. Tests do not acquire dependencies or build a missing native executable. Native POSIX behavior is actually verified on macOS only; Linux source suitability is not execution evidence. Windows returns unsupported rather than presenting a fake PTY. No ConPTY, three-platform release readiness or adoption claim.

## OpenCode SQLite difference slice (ticket 04)

The explicit isolated Rust selection composes `NativeOpenCodeReader`; default Python readers and shared stores remain unchanged. Vendor-local native `observe` reads the OWN `opencode.db` through the macOS system SQLite C API, using read-only connections and a 250 ms busy timeout for every prepared query. This is a required OS library dependency, not a dependency-free or three-platform adoption claim. SDK `sqlite3.h` and the linker stub are build inputs; the loaded system library may live in the dyld cache. The finite local linkage probe records its loaded name/version/UUID, without full dylib/cache byte closure.

Native code interprets SQLite usage, separate `part.rowid` activity progress, marker lookup, session existence and metadata; Python retains discovery paths, common prompt presentation, the unchanged SQLite checkpoint/anchor spelling, persistent usage/checkpoint ownership and restart dedup. Completed assistant messages are credited; incomplete rows remain pending. Historical activity is skipped on first observation, and only a top-level `step-finish(reason="stop")` settles a turn. BUSY/LOCKED remain numeric SQLite outcomes, not message-text classification or a Python interpretation fallback.

`native OpenCode production-client WAL SQLite and resume syntax variant` in `tests/cli/nativeDifferences.test.ts` is the principal case. It uses the unchanged real resume builder and temporarily replaces only the OpenCode declaration's `resumeArgs` with its existing supported `-s` form, restoring the original reference in `finally`; the shipped `--session` default is unchanged. The synthetic producer publishes pending usage, tool/child non-settlement, top-level completion and a durable restart; the pane carries the renderer's spawn metadata, so stage 1 has no session ID until the existing marker binding detects it.

## Native differences and locality (ticket 04)

Two bounded baseline cases run through the production TS WS client, authenticated Python handlers and stores, the Rust sidecar and the macOS PTY; only the external CLI (a synthetic peer) and its vendor data are substituted:

- **Codex** (`native Codex production-client delayed identification and resume`): the session ID is not known at launch and is identified later from the rollout; both the old `event_msg/user_message.message` and the newer `event_msg/item_completed` `UserMessage.content[].text` prompt formats are read natively (`src/codex.rs`) while Python presentation is unchanged; resume uses `codex resume <id>`; persisted checkpoints survive a backend restart.
- **OpenCode** (above): no session ID at launch, marker-based delayed identification, WAL SQLite usage/activity with pending, child and completion boundaries, durable restart totals and checkpoint, and the `-s <id>` resume syntax.

Vendor code stays local: `cli_runtime_codex.py`/`cli_runtime_opencode.py` and `src/codex.rs`/`src/opencode.rs` implement interpretation; `cli_runtime_adapters.py` (`NATIVE_VENDORS`), `src/adapters.rs` (`integrated`/`observe`) and the registry's reference wrappers are the only rosters. Shared orchestration gains no vendor branch: `posix.rs` replaced its Claude-only create/observe gates with the roster, `cli_runtime.py` admits the roster and adds a vendor-generic `observe_native`, and the WS handlers, log watcher, attribution and stores are unchanged. New observe modes (`identify`, `has_session`, `usage`, `legacy`, `activity`) map one-to-one to existing reader methods; no new capability kind was introduced.

Coverage and outstanding work, recorded rather than fixed here:

- Child (sub-agent) OpenCode activity keeps the existing empty pane attribution; a resumed explicit-ID shared-database pane has no live-scan file hint until a token event, so its usage is credited at the shutdown flush.
- On this macOS host the watcher does not report WAL-only appends, and an OpenCode data directory created after backend start is not watched until the next rescan; the fixture publishes every phase by checkpoint and precreates its empty data directory. WAL-only reads, the restart cursor and BUSY/LOCKED/no-data handling are covered by the native sidecar and Rust tests, not by the WS principal.
- Codex native `turns` is not integrated; the remaining registry vendors (`aider`, `antigravity`, `copilot`, `cursor`, `droid`, `grok`, `kilo`, `kimi`, `mcode`, `muse`, `pi`, `qwen`) have no native composition. Evidence is macOS only; one Rust test pins the host's system SQLite version and UUID.
- These slices are not complete Codex or OpenCode adoption. The isolation harness under `backend/tests/cli_regression/support/` and `backend/tests/isolation_guard/` is kept for reuse by later validation work.

## Private protocol 1

Python starts one lazily initialized executable per backend with `--protocol 1 --runtime-generation <fresh-token> --owner-pid <backend-pid>`. `ready` reports actual PID, owner, generation, version/platform and PTY implementation. Python checks identity/readiness and records executable SHA256 plus OS creation time before native create. There is no socket, provider transport, generic broker or STT abstraction.

UTF-8 JSONL requests contain strictly increasing runtime-wide `id: rN` (positive u64), `runtime_generation`, `op`, and `args`; session operations add `session_id` and `session_generation`. A mismatched generation is rejected. Replies correlate ID with `ok/result` or structured `error {code, stage, message}`. Lifecycle/output events carry the two generations and session/pane/workspace identity. PTY output remains raw bytes in `data_b64`, with monotone `seq`, byte `offset` and `dropped_before`; frontend UTF-8 decoding remains production code.

Operations are `create`, `activate`, `write`, `interrupt`, `kill`, `resize`, `release`, `flow`, `state`, `cancel`, `ping`, and `shutdown`. Native creates publish an ownership receipt before Python confirms durable registration and successful outward create; activation prevents early output escaping routing. Exit and cleaned receipts report exact status, output watermark, root reap and survivor/unverifiable identities. Cleanup keeps bounded PTY reads active while waiting to reap a signaled root: a blocked PTY write must progress before termination can complete. These bytes retain the same bounded publication/drop accounting and precede the exit watermark. A natural early exit is reaped evidence, never a fabricated live process.

One bounded FIFO controller and independent native IO loop per live session preserve admitted write/control order. Request histories are a scalar counter; confirmed settled session views retain at most 256 entries. Python has at most 256 pending private RPCs; native control/session operation queues are bounded at 256. Incoming requests are bounded at 32 MiB and outgoing lines at 64 KiB (raw read chunks <=16 KiB). Native publication and Python presentation use 5-MiB per-session raw-byte caps with drop-oldest accounting, existing one-second reader pause ceiling and pending-input semantics (500-ms blocked notice). These are raw-byte budgets, not a promise that JSON/base64/record overhead has no memory cost.

Lifecycle/control may overtake data only privately. Python settles and drains/accountably drops the recorded output watermark before public exit or resize ACK. A per-session Python control transaction owns resize/redraw/reattach through public ACK and release of its operation-local token. Multi-session reattach acquires unique locks in sorted order. Native resize immediately rejects an already-held fence without draining/overwriting it or waiting behind a queued release. Cancellation preserves matching cleanup before unlocking. Resize seals the old-width prefix at native admission and holds subsequent reads until public ACK/release; ordinary output is not truncated with a short terminal-record read buffer. Public output/exit/resize shapes are unchanged, and scrollback is never cleared.

`ping.bookkeeping` exposes bounded verification counters: last request, live/settled sessions, workers, queued output bytes/max per session and nonempty output queues. These are not a public API or benchmark claim. Cancellation, lost-ACK, replacement and sidecar-death handling are described in the ticket-05 section below.

## Claude reference (ticket 03)

`shared/agent-cli/claude.json` is the reference's declarative authority. `uv --project backend run python scripts/generate-claude-facts.py --check` checks typed TS/Python/Rust consumers without writing. Existing specs retain their public shape. Only explicit isolated evaluation composes `NativeClaudeReader`; default callers and all other vendor specs keep their existing readers. Discovery, session existence/cross-project search, resume command recognition and common prompt presentation remain Python. JSONL record interpretation is native; selected failures do not run the Python Claude parser.

`create.args.agent_key` is empty for an ordinary shell or `claude` for this reference. Native Claude uses its declared graceful=true, grace_s=3.0, defer_master_close=true, including force requests; ordinary-shell policy is unchanged. Python retains the wrapped shell command, env precedence/removal, credential/quota policy, per-vendor switch lock, rollback, MCP/skills/hooks config writing, login rewrite and application ownership. The report/GO handshake is retained in Python for the vendors that declare live-file discovery; Claude does not declare that capability, so no new Claude handshake is invented.

Private `observe` requests use the existing sidecar and runtime generation, with `{vendor, path, mode, checkpoint, seen, expected_anchor_b64, anchor_invalid}`. Process-unbound/settled observations use one lazily started history worker with a 256-request bounded queue, not the shared stdin admission loop. It retains request/runtime correlation and the existing worker-count/teardown deadline; it invents no live-session ownership and no filesystem-syscall cancellation guarantee. Modes are `usage`, `session_usage`, `activity`, and `turns`. A matching retained Claude PTY contributes its runtime/session/pane/workspace attribution and validates the session generation; historical observation is explicitly process-unbound. Rust opens the actual file and returns parser/path/file identity, native session/cwd, interpreted records and next cursor. Correlated `observation` parts carry consecutive indices and base64-encoded result bytes before a final reply declaring `observation_parts`; each wire record stays below 64 KiB. Full application result lists retain the baseline's potentially unbounded size; this is a wire bound, not a constant-memory parsing claim.

Python converts 512-byte checkpoint anchors to/from the existing BLAKE2b spelling but does not parse JSONL. Usage consumes only newline-complete records and retains the last 64 accepted call keys. Activity retains its separate physical-line high-water, including valid unterminated records and intentionally no reset on truncation. A decoded non-object activity record still fails, but its correlated observation parts carry the inherited physical-line progress before the final `ok:false` reply. Python validates parser/path/native session/runtime/ownership, an advancing high-water and unchanged prior non-marker keys, applies that progress, then propagates the first error. It neither returns the earlier partial events nor silently treats the exceptional record as successful corruption skipping. The next poll can reach the following completion.

Existing durable Python stores decide when checkpoints are committed, including shutdown drain. The PTY sweep awaits cleanup acknowledgment for retained ownership, including naturally exited roots, and checks errors after acknowledgment/event completion. Successful unregister precedes the fence return; waits are bounded. Observation remains available until the existing Python drain completes; backend-owned pipe EOF then terminates the sidecar.

Principal verification is `mise exec node@22.23.2 pnpm@10.0.0 -- pnpm test:run --project cli tests/cli/claudeRuntime.test.ts`: the production TS WS client, authenticated Python handlers/stores, the actual hashed sidecar and macOS native PTY. It covers child-observed production command/config/model/effort composition, native usage/activity/turn completion, durable checkpoint restart, persisted resume and owned cleanup. The selected missing-binary case must refuse without launching a child/Python PTY; it does not claim a native process ran. These functional cases execute in default `pnpm test:run` on their declared macOS host. The CLI catalog/reporter links their executed post-assertion receipts and required outcomes separately from frontend vendor-spec unit contracts.

`backend/tests/test_cli_runtime_claude.py` provides supplementary real Python-WS credential/re-wake/quoting/checkpoint/error-progress evidence; `test_cli_runtime_claude_parity.py` supplies native-protocol parity and wire-bound checks. Controlled external vendor data/executables and the optional sandbox credential-store boundary are the substitutes, not successful runtime/handler/parser behavior. Native-reader composition and correlated native receipts support Rust interpretation; there is no fail-on-legacy-parser tripwire. The old frozen-r2 handoff's claim of explicit Python-parser rejection is invalidated, not implemented retroactively. No actual Claude/provider execution, packaging, cross-platform adoption or benchmark result is implied.

## Cancellation, runtime loss and existing conversation recovery (ticket 05)

Scope: a macOS-only evaluation of the minimal design, through the existing terminal and recovery interfaces. It adds no user-facing setting and no Host/Plugin contract change. Its sidecar (Rust) changes are confined to the private runtime protocol: the ownership gate and journal (`--ownership-journal`, the `ready.ownership_gate` field) and the per-create cancellation state machine behind the existing private `cancel` op (see the ownership-gate and cancellation paragraphs below). Native Linux/Windows execution is **pending ticket 08** and is not claimed by any mocked or macOS test.

**Abandoned creates.** A `terminal.create` whose caller disappears after the request reached the sidecar (handler task cancelled by a WebSocket loss, the real 15 s request timeout, or cancellation while awaiting the ownership receipt) is not dropped. `RustTerminalService._abandon_launch` registers an internal `abandoned` session (never presented to a renderer, its output dropped) before any sidecar event for it can be read, sends the existing private `cancel` (an optimization), awaits the create's own answer, and drives any child that was spawned to `kill` + the sidecar's `cleaned` acknowledgement. A refused create needs nothing. A same-pane or same-conversation (resume id) launch waits for that resolution (`CREATE_BLOCKED` after 30 s) and the abandoned create is never re-issued. An answer that never comes within 20 s is a runtime loss (the replacement cannot be proven not to overlap).

**Runtime loss with Python alive.** The first of reader EOF/protocol error or a failed event task (for a runtime that completed its handshake) starts `_invalidate`: fail every wait with the runtime error, end the sidecar through the owned process handle, cancel and drain the old generation's tasks, run `pty_registry.reap_runtime(generation)`, present one `terminal.exit` per lost session with `reason: "runtime_lost"` (`exit_code`/`signal` null; the existing payload, only a new reason string) **after** cleanup, and only when cleanup is complete clear the failure so the next explicit operation starts a fresh generation. Incomplete or unverifiable cleanup keeps every create and observation refused with `CLEANUP_FAILED`. Startup, version and handshake failures keep their earlier semantics (permanent, explicit, no Python fallback). Receipts: `runtime_invalidated` (counts only) and `abandoned_create`.

**Identity-verified cleanup.** `reap_runtime` considers only registry entries recorded by this backend under exactly the lost generation. Roots need group-leader status and a matching start time; descendants are the last persisted snapshot's pids that still match their start time; the force round is re-verified against a fresh table; a failed process snapshot signals nothing. Another generation or runtime, another backend's entries, a forged/recycled identity and every unrecorded process are never signalled.

**Documented limit.** Descendants are known only through the sidecar's periodic snapshot (first 5 s of a session, then every 30 s). A descendant that detached after the last persisted snapshot is unknown, therefore not signalled; killing the sidecar also closes the PTY master, which only reaches processes still attached to that terminal. Tests wait for the snapshot before killing the sidecar.

**Distinguished causes.** WebSocket loss keeps every PTY (reattach `alive`, same child). Runtime loss presents `terminal.exit(runtime_lost)` and reattach answers `dead`. Backend death ends the sidecar through stdin EOF with its owned trees (a restarted backend answers `dead`; the registry entries left behind are dropped by its startup reap without signalling anything).

**Existing recovery, unchanged.** The renderer maps `terminal.exit` with reason `runtime_lost` to the existing lost-PTY owner callback (`useTerminal.ts`); `src/renderer/src/lib/ptyLostRecovery.ts` holds the extracted setting/visibility gate that `App.vue onPanePtyLost` already applied (visibility captured when the loss is reported). Resumability, session-existence, rebuild locks, busy gating, `offerContinue` (a button, never an automatic injection) and manual Rebuild for other panes are the unchanged `rebuildPaneViaResume` path. Nothing replays input or resumes every pane.

**Evidence.** Production TS WS client → authenticated Python → actual sidecar → macOS PTY: `tests/cli/runtimeRecovery.test.ts` (driver `backend/tests/cli_regression/support/runtime_recovery_driver.py`; faults are SIGSTOP/SIGKILL on the sidecar or backend after pid + create-time verification, fixture executables, a replaced runtime file). Supplements with the real sidecar: `backend/tests/test_cli_runtime_recovery.py`, `backend/tests/test_pty_registry_runtime.py`; renderer: `ptyLostRecovery.test.ts`, `useTerminal.runtimeLost.test.ts`. Not proven here: PID reuse on a real recycled pid (stood in by forged-identity entries) and any non-macOS behaviour.

**Unresolved launches (review-1 corrections).** A dispatched create whose spawn identity is not yet durable is tracked in memory from dispatch. If the sidecar reported the identity (`owned` read, registry write still in flight) the generation's cleanup uses that identity exactly like a registry entry (`reap_runtime(..., known=...)`), and a registration that completes after the generation was retired is undone by generation-bound `unregister_owned`. If no identity was ever reported (a child may exist that nothing names) the generation is **not** declared clean: `runtime_invalidated.complete` is false, `CLEANUP_FAILED` fences every later create/observation, and the unknown child is deliberately never signalled by pid. Any failed process-table read while verifying cleanup (including later reads) is `unverifiable` and keeps the identities. A failed abandoned-create cleanup and a native `cleaned` failure both retire the runtime through the same invalidation with the incomplete fence; the replacement barrier opens only together with that fence. A create cancelled by the renderer while Python still coordinates it (`CreateCancelled`, checked just before dispatch) never reaches the wire. A cleanup wait that really times out (12 s) is the existing `CREATE_REAP_TIMEOUT` refusal.

**Ownership gate and journal (review-2/3 corrections; the sidecar changes of ticket 05, with the cancellation state machine below).** When started with `--ownership-journal <file>` (the Python service always passes `<data>/runtime-ownership/<generation>.jsonl`, created atomically with an owner header before the sidecar exists) the sidecar gates every PTY root: the forked child does the unchanged PTY setup (`setsid`, signal defaults, `TIOCSCTTY`), then — still inside `pre_exec`, before `exec` — reports its pid on a pipe and blocks on a gate pipe. The sidecar's watcher takes the root's identity, appends one JSON line (`pid`, `pgid`, start identity, `argv0`, session and runtime generation, `owner_pid`), `fsync`s it, and only then writes `G` to the gate. EOF on the gate (the sidecar died, or the journal refused) makes the child fail its own spawn, so **the target program never executes unless its identity is durable**: a sidecar `SIGKILL` at any point before the journal is durable, or a journal open/write/fsync failure, leaves no executed target, no detached child and no process (proved with the real sidecar: a FIFO journal holds the append; the root is a fixture that records "I ran" as its first action and starts a detached HUP/TERM-immune child). `pre_exec` uses only raw `close`/`write`/`read`/`getpid` on integers (async-signal-safe); the gate's pipes are `FD_CLOEXEC`. The `ready` event reports `ownership_gate`; without the option nothing changes (no gate, no journal), which is how the 02-04 harnesses and an older sidecar behave. The root's session, process group and controlling terminal are unchanged (the gate is the last step of `pre_exec`; a normal-path test asserts `sid == pgid == pid`, the PTY as controlling terminal, and the journalled identity).

**Concurrency cost.** Pipe creation and the `spawn` of a gated root are serialised process-wide (one lock) so that no concurrent fork can inherit the gate's write end — which would keep the gate open after the sidecar's death. The lock is therefore held across the journal append and its `fsync`: **creates are serialised through the journal append** (one `fsync` per create, on the order of a millisecond on local storage; a hung journal hangs the create until Python's 15 s request timeout, the root staying gated and never executing). Correctness was chosen over parallel spawn. Other `fork`s in the sidecar (none on macOS on the hot path) are not under this lock.

**Startup after an unclean run.** A restarted backend ingests the journals of dead backends into the registry (the file is kept), cleans each named root by exactly the existing identity rules, and deletes a journal only after a final recheck against a fresh process table shows every identity it names gone. A torn, empty, unreadable or un-ingestable journal, a survivor, an unreadable process table, or a failed registry write leaves the journal and rows in place and **fences runtime admission** (`terminal.create` and observation through the Rust runtime refuse with `CLEANUP_FAILED: ownership unresolved at startup (...)`; the error is also logged at ERROR with the journal kept). The fence is recomputed from the preserved evidence on every admission attempt, so it lifts by itself once the evidence is resolved by a **verified** cleanup. The only supported recoveries are: (a) **identity-bound repair** — restore the damaged journal to its true content (for a torn journal, remove only the incomplete trailing line, never a complete line, never the file) and retry; the next admission re-runs the cleanup, kills each journal-named root by its recorded identity, verifies it gone and then lifts the fence; or (b) a **full machine restart**, after which every orphan is gone. **Deleting a journal or a registry row that still names an unresolved process is an unsafe bypass, not a recovery procedure, and the product does not offer it**: with the evidence gone the backend would admit a new runtime while the orphan may still be alive and unnamed, which is exactly what the fence exists to prevent. If such an override is ever wanted it is a separate, explicit user decision that accepts the orphan risk and cannot be reported as verified cleanup. A journal and a registry row that name the same pid with different identities (start time, owner or generation) are kept side by side. The older row is dropped only once every identity it records is verified gone: a pid now held by a process with a different birth proves the row's root dead, so its recorded descendants are signalled by their own start identities and must be confirmed gone; a survivor, an unreadable verification snapshot, or a row whose root start is unknown keeps the row (with its descendants), the journal and the fence. Only then is the journal's root ingested and verified.

**Cancellation while the ownership gate is held.** The renderer's `terminal.create.cancel` for a create that is already on the native wire is not acknowledged on a flag alone. Python sends the sidecar's `cancel` for that request. The sidecar keeps one cancellation state machine per create (`Queued` → `Cancelled` | `Released` → `Registered`), and every transition and every verdict happens under its single registry lock. `prevented` is answered only while the gate is still closed, and the release step consults the same state under the same lock. So a cancel that wins refuses the gate: the root's `pre_exec` fails and the target never executes. That verdict is the proof the handler needs to acknowledge `cancelled: true`, even though the journal write is still held and resumes later. A cancel after the release is answered `released`; the session is then closed when it is published. A cancel after publication is answered for the registered session, and a create whose answer is already gone gets `unknown`. None of these is a proof. In those cases the handler waits (bounded) for the transaction's own disposition: a refusing answer, or the created root cleaned by its verified identity (before publication inside `create_async`, which re-checks cancellation after the owned wait and again right before handing the session over, or after publication by the handler's rollback). Until a session is handed over it exists only as a hidden provisional session, registered at its `owned` event, so a cancel-driven exit is never a protocol error. If no proof is obtained the handler answers `CREATE_CANCEL_UNRESOLVED` instead of `cancelled: true`. The handler decides success versus cancellation once, before the success response can yield: it checks the cancellation flag and commits the create in one synchronous step, and only then sends the success. A cancel that finds the create committed is no longer cancelling a pending create; it answers `cancelled: false` and the client closes the term normally. So a create id never receives both a success and a cancellation error. A connection that dies during that success send rolls the term back, as on any disconnect. A sidecar started without `--ownership-journal` has no gate, so a `prevented` answer is not treated as proof there (the same wait-and-clean path applies).

**Remaining limits.** (1) macOS only; the gate is written for POSIX and unexercised on Linux/Windows (ticket 08). (2) A root that ignores `SIGKILL` cannot exist, but an identity can stay unresolved (process table unreadable, signal permission); it fences, it is not guessed. (3) Descendants that detached after the last persisted ownership snapshot (first 5 s of a session, then every 30 s) are unknown, so they are not signalled (accepted boundary). (4) Between the gate release and the first descendant snapshot the root may spawn a detached child that only the root's own group/session kill reaches. (5) A journal line is written with one `write_all`; a short write is detected on the next read as a torn line (fence), not prevented. (6) An empty (zero-byte) journal is **unverifiable**, not proof that nothing was spawned: Python writes and fsyncs the owner header to a temporary file before renaming it into place, so a zero-byte final journal may be a once-valid journal that was truncated or corrupted, and the root it named may still be alive. It is kept and fences admission until an identity-bound recovery (restoring its true content, then a verified retry) or a full machine restart; deleting it is the unsafe bypass described above, not a fix. (7) Real PID recycling cannot be forced on macOS (forged identities stand in). (8) The gate does not apply to sessions created by a sidecar started without `--ownership-journal`.

**One retirement rule (review-9).** Every handler that retires a pane — `manual_pane.release_pty`, `manual_pane.unspawn`, `pipeline.slot_unspawn` and `pipeline.slot_unspawn_by_pane` — settles the pane's terminals *before* touching any record. Settlement covers in-flight creates (still being handled on any connection), using the cancellation proof rules above, and published sessions (verified native kill), for the pane id and its former ids. Anything unproven is answered with `PANE_RELEASE_UNRESOLVED` and changes no record. In the renderer, `onKill` (through `lib/paneRetirement.ts`) treats only a proven answer as retirement. A refusal, a timeout or a transport failure keeps the pane, its terminal ref and its record, shows the existing error, and starts no replacement (Rebuild, idle reclaim, pipeline restart, stage refill and workspace close all check it).

**Backend admission limit (documented, not enforced).** The backend does not guarantee a unique live PTY per pane id against an independent authenticated sender. `terminal.create` serialises one connection's requests per pane and caches a matching generation, but it does not refuse a new generation because another live CLI already runs under the same pane id. For the product client, uniqueness comes from the renderer's per-pane create fence plus the retirement rule above (no replacement before proven settlement). A second authenticated client that issues its own `terminal.create` for a pane id already in use is outside that guarantee.

**Dock-window close and binding (review-10).** `terminal.kill_surface`, sent when a window closes its embedded panels, now settles that window's in-flight panel creates (matched by the surface and workspace recorded on the create transaction) using the same proof rules before it ends published panels or retires any record. If one cannot be proven, it answers `PANE_RELEASE_UNRESOLVED` and retires nothing. The main process still sends it fire-and-forget; the guarantee is the backend's. `pipeline.slot_unspawn` and `manual_pane.unspawn` bind their store write to the pane ids they settled. If the slot, or the session match, resolves to a different pane by the time of the write, nothing is retired and the request answers an error.

## Comparison and G1 outcome (ticket 06)

A matched Python/Rust comparison on one macOS arm64 machine through the production seam (TS WS client → Python handlers → sidecar → native PTY; only the external CLIs and provider data are synthetic). Method 8 (`docs/testing/agent-cli-runtime-baseline.md`) reuses the G0 workload unchanged and adds the runtime mode, per-component accounting, an empty-started-idle phase, repeat-major interleaved order (5 repeats × 1 and 4 sessions × 2 arms = 20 attempts, one run) and a per-trial proof that the Rust arm ran the real sidecar and native PTY. Raw receipts, summariser, decision program and the full report are kept under `.scratch/agent-cli-runtime-evaluation/evidence/t06/` (not tracked).

**Outcome under the pre-registered rules: STOP** (an adverse distinguishable cost on decision metrics with no evidence-backed maintainability or lifecycle counterbalance). It is not an adoption verdict and not a claim about the language: no numeric budget was set, and CONTINUE would additionally have required every adverse mechanism explained and the locality finding cleared.

- **Cost (Rust vs Python, n = 5 per cell, distinguishable = non-overlapping ranges).** Higher in the Rust arm: create acknowledgement (first +10 ms, warm +2.5 ms), active CPU (combined 2.7 → 6.0 % with one session, 5.5 → 16.6 % with four), live-idle CPU (+0.6 % per live session), combined RSS (+3–4 MiB), `io_ms` p95 (+0.07–0.27 ms), and a four-session kill (344 → 1012 ms). Lower: backend RSS (−0.4 to −1.1 MiB) and four-session warm-shell and agent readiness. Cold start, first/warm shell readiness and `io_ms` medians are not distinguishable at 1 session.
- **Mechanisms.** The per-create ownership journal with a full-durability sync (`posix.rs` `journal_append`) explains the acknowledgement cost; an unconditional 1 s sleep on every non-forced kill outside the Claude-keyed branch (`posix.rs` `cleanup`) explains the kill time; a 2 ms poll per live session explains idle CPU; the second process explains the RSS. Active CPU, helper CPU, `io_ms` p95 and burst scaling are not explained to size. These are measured observations about this implementation and its process boundary; nothing in the evidence isolates an effect of the Rust language (no comparable Python sidecar, no reader benchmark, and the mapping of the sync call to `F_FULLFSYNC` was not verified). A non-matrix check (real service classes, 300 echo rounds) shows +3 ms per round that the matrix's 5 ms polling cannot resolve.
